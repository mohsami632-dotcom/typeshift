## 1. What typeshift Does (In Plain Language)

**typeshift** is a command-line tool and TypeScript library that translates data schemas between four common formats:
- **TypeScript interfaces & type aliases**
- **JSON Schema (Draft-07)**
- **Zod schemas**
- **OpenAPI 3.1 component schemas**

Instead of building separate converters between each pair of formats, typeshift translates everything through a central internal model called `SchemaIR`. Crucially, when you convert from a format that enforces runtime validation rules (like JSON Schema regex or number limits) into a format that cannot enforce them (like static TypeScript interfaces), typeshift inspects both formats and alerts you to every constraint that had to be dropped. You can also configure it to fail your CI build (`exit code 2`) if constraints are lost.

## 3. The Problem It Solves

Modern web and backend applications rarely use just one schema representation:
1. **Compile-time safety**: TypeScript interfaces in application code.
2. **Runtime boundary validation**: Zod schemas validating API inputs or form submissions.
3. **Data interchange & contracts**: JSON Schema for Kafka events, database validation, or webhooks.
4. **Public documentation**: OpenAPI 3.1 for API specs and SDK generation.

### The Two Underlying Hard Problems:
1. **Combinatorial Complexity**: With $N$ formats, maintaining point-to-point converters requires $N \times (N-1)$ translation paths (12 paths for 4 formats; 30 paths for 6 formats), each with different CLI flags and idiosyncrasies.
2. **Mismatched Format Expressiveness**: Different formats have fundamentally different capabilities. A JSON Schema or Zod validator can enforce `minimum: 18`, `pattern: "^[A-Z]{3}$"`, or `format: "email"`. A compile-time TypeScript interface cannot enforce runtime numeric bounds or regexes. Many existing converters silently ignore or drop these constraints without telling you.

## 5. Current Scope & Honest Limitations

*Be completely transparent about what typeshift does NOT do yet. HN respects honesty:*

- **OpenAPI Scope**: Currently compiles data models under `components.schemas`. It does **not** compile HTTP route handlers or request/response pipelines under `paths` (typeshift is a schema data model compiler, not an RPC client generator like OpenAPI-fetch or Orval).
- **OpenAPI File Formats**: Requires JSON format (`.openapi.json` or `.json`). Native YAML parsing is planned for v0.3.0 ([issue #5](https://github.com/mohsami632-dotcom/typeshift/issues/5)).
- **TypeScript Static Types**: TypeScript interfaces cannot enforce runtime validation bounds like `minimum` or regexes at compile time. typeshift preserves structural types and descriptions as JSDoc comments, while surfacing warnings.
- **Dependencies**: Uses the official TypeScript Compiler API (`typescript`) for AST analysis and `commander` for the CLI.

## 7. Factual Notes for Likely Community Questions

### "How does this compare to `quicktype`?"
- **Factual Difference**: `quicktype` focuses on one-way generation of client models in 20+ programming languages (Go, C#, Swift, Rust) from JSON samples or JSON Schema.
- `typeshift` focuses specifically on bidirectional conversion between the core schema formats used in TypeScript/JavaScript stacks (TS, Zod, JSON Schema, OpenAPI), with a formal capability matrix and explicit loss diagnostics to catch silent constraint degradation.

### "How does this compare to `zod-to-json-schema` or `json-schema-to-typescript`?"
- **Factual Difference**: Those are excellent single-purpose tools for specific format pairs. However, combining them requires maintaining multiple packages with different configurations and AST interpretations.
- `typeshift` uses a single shared Intermediate Representation (`SchemaIR`) with $2N$ operations, and introduces automated information-loss detection and CI exit codes (`--loss-policy error`).

### "Why not support OpenAPI `paths`?"
- **Factual Reason**: Generating client code for HTTP endpoints requires opinionated assumptions about HTTP clients (Fetch vs Axios), authentication middleware, URL encoding, and retry policies.
- `typeshift` remains strictly a **schema data model compiler**. It leaves routing and transport to specialized tools and focuses on keeping data contracts and types in sync.

### "Why no YAML support yet?"
- **Factual Reason**: Node.js does not have a native YAML parser in the standard library. For v0.2.0, dependencies were kept minimal (`typescript` and `commander`). Native YAML parsing is tracked as [issue #5](https://github.com/mohsami632-dotcom/typeshift/issues/5) for v0.3.0.
